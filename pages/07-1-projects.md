# 07-1. 프로젝트: 반복 업무를 위한 나만의 AI 작업 공간 만들기

## 1. 이 강의에서 배울 내용

ChatGPT 프로젝트는 하나의 업무에 필요한 채팅, 파일, 지침과 연결된 소스를 한곳에 모아 장기간 이어서 일하기 위한 작업 공간입니다. 새 채팅을 열 때마다 같은 배경을 다시 설명하거나 같은 파일을 반복해서 올리는 일을 줄일 수 있습니다.

이 강의에서는 가상의 컨설팅 프로젝트를 문의 접수부터 계약 검토까지 진행하며 다음 내용을 익힙니다.

* 프로젝트가 일반 채팅과 다른 이유를 이해합니다.
* 프로젝트 지침과 소스의 역할을 구분합니다.
* 결과물의 목적에 따라 채팅을 나눕니다.
* 새 자료가 추가됐을 때 기존 결과를 업데이트합니다.
* 여러 문서의 일치, 변경, 누락과 새 조건을 구분합니다.
* 공유와 민감정보 관리 원칙을 확인합니다.

핵심 원칙은 다음 한 줄입니다.

> 지침은 짧게, 사실은 소스로, 채팅은 결과물의 목적별로 관리합니다.

## 2. 프로젝트가 필요한 업무

다음 조건 중 두 가지 이상에 해당하면 일반 채팅보다 프로젝트가 적합합니다.

* 같은 주제로 여러 번 다시 돌아와야 합니다.
* 여러 파일과 연결된 소스를 계속 참고해야 합니다.
* 새 자료가 들어오면서 기존 결과가 바뀝니다.
* 요구사항, 결정과 변경 이력을 함께 관리해야 합니다.
* 서로 다른 결과물을 여러 채팅에서 만들어야 합니다.

예를 들어 고객사 컨설팅, 장기 리서치, 정기 보고, 채용, 교육과정 개발처럼 자료와 결정이 누적되는 업무가 여기에 해당합니다.

반대로 한 번의 질문으로 끝나고 공통 자료가 필요하지 않은 일은 일반 채팅이 더 간단합니다.

| 구분 | 일반 채팅 | 프로젝트 |
| --- | --- | --- |
| 적합한 일 | 한 번에 끝나는 질문·작업 | 장기간 이어지는 하나의 업무 |
| 공통 맥락 | 현재 대화 중심 | 프로젝트의 지침·소스·관련 채팅 |
| 파일 사용 | 해당 요청에 필요한 파일 첨부 | 여러 채팅에서 함께 쓸 소스 관리 |
| 대화 구성 | 질문 흐름에 따라 이어짐 | 결과물의 목적별로 채팅 분리 |
| 변경 관리 | 새 대화에서 다시 설명할 수 있음 | 새 소스를 추가하고 관련 결과를 갱신 |

## 3. 프로젝트를 이루는 세 가지 요소

### 3.1 프로젝트 지침

지침에는 모든 채팅에 공통으로 적용할 역할과 작업 원칙을 적습니다.

* ChatGPT가 맡을 역할
* 우선할 기준
* 자료가 충돌할 때의 판단 원칙
* 자료에 없는 내용을 처리하는 방법
* 공통 출력 원칙

금액, 날짜, 인원처럼 자주 바뀌는 사실을 지침에 길게 넣지 않습니다. 이런 사실은 소스에서 관리해야 변경하기 쉽습니다.

### 3.2 프로젝트 소스

소스는 업무의 사실과 근거를 담습니다.

* 이메일과 상담 기록
* 제안서와 계약서
* 회의록과 결정 기록
* 데이터 파일과 참고 문서
* 연결된 서비스에서 가져온 자료

문서마다 내용이 다를 수 있으므로 작성일, 버전과 승인 상태를 확인해야 합니다. ChatGPT가 프로젝트 소스를 참고하더라도 최종 사실 확인은 사람이 담당합니다.

### 3.3 목적별 채팅

하나의 긴 대화에 모든 일을 넣지 않고 결과물의 목적별로 나눕니다.

* `01. 고객 문의와 요구사항 정리`
* `02. 제안서와 고객 요구사항 검토`
* `03. 계약서 검토와 프로젝트 준비`

시간 순서가 아니라 결과물의 목적이 채팅을 나누는 기준입니다. 그래야 필요한 결과를 다시 찾고 업데이트하기 쉽습니다.

## 4. 실습 상황과 준비

가상의 유통회사 ‘다온유통’은 다섯 개 지점의 월간 실적 파일을 수작업으로 합치고 있습니다. 보고서 작성에 이틀이 걸리고 복사·붙여넣기 과정에서 오류도 발생합니다. ‘로도스 컨설팅’은 Power Query를 활용한 월간 보고 자동화 컨설팅을 제안합니다.

실습에서는 다음 자료가 순서대로 들어온다고 가정합니다.

1. 최초 문의 이메일
2. 전화 상담 전사
3. 컨설팅 제안서
4. 제안서 검토 회의록
5. 계약서 초안

실제 회사 자료 대신 개인정보와 기밀정보가 제거된 샘플 파일을 사용합니다.

## 5. 프로젝트 만들기

메뉴 위치와 이름은 앱 버전이나 사용 환경에 따라 달라질 수 있습니다. 현재 화면에서 프로젝트 만들기 기능을 찾아 다음 순서로 준비합니다.

1. 새 프로젝트를 만듭니다.
2. 이름을 `다온유통 월간 실적 보고 자동화 프로젝트`로 지정합니다.
3. 프로젝트 지침을 입력합니다.
4. 최초 문의 이메일, 전화 상담 전사와 제안서를 소스로 추가합니다.
5. 세 파일이 소스 목록에 보이는지 확인합니다.

다음 지침을 입력합니다.

<pre><code>당신은 다온유통의 월간 실적 보고 자동화 컨설팅 프로젝트를 돕는 업무 도우미입니다.

프로젝트에 첨부된 자료를 참고해 답변해 주세요.
자료마다 내용이 다르면 작성일과 진행 순서를 고려해 가장 최근에 합의된 내용을 우선해 주세요.
자료에 없는 내용은 임의로 추정하지 말고 확인이 필요하다고 알려 주세요.</code></pre>

이 지침에는 금액이나 일정 같은 개별 사실이 없습니다. 여러 채팅에 공통으로 적용할 역할과 판단 원칙만 담았습니다.

## 6. 실습 1: 고객 요구사항 정리

프로젝트 안에서 새 채팅을 만들고 `01. 고객 문의와 요구사항 정리`라고 이름을 붙입니다.

<pre><code>최초 문의 이메일과 전화 상담 전사를 참고해서 이번 프로젝트의 요구사항을 정리해 주세요.

현재 업무, 발생하는 문제, 원하는 결과, 확인된 조건, 제외 범위, 아직 확인되지 않은 사항으로 구분해 표로 작성해 주세요.

각 항목의 근거가 된 파일도 함께 표시해 주세요.</code></pre>

결과에서 확인할 것은 문장의 모양이 아니라 근거의 결합입니다.

* 현재 업무와 문제점이 문의 이메일에 근거했는가?
* 제외 범위와 추가 조건이 상담 기록에서 반영됐는가?
* 확인되지 않은 내용을 임의로 단정하지 않았는가?
* 각 항목을 원문에서 다시 찾을 수 있는가?

두 문서의 내용이 하나의 표에 근거와 함께 정리되면 첫 번째 실습이 완료된 것입니다.

## 7. 실습 2: 제안서 검토와 변경 관리

요구사항 정리와 제안서 검토는 결과물이 다르므로 새 채팅을 만들고 `02. 제안서와 고객 요구사항 검토`라고 이름을 붙입니다.

<pre><code>고객의 최초 문의 이메일과 전화 상담 내용을 기준으로 컨설팅 제안서를 검토해 주세요.

일치하는 내용, 제안서에 추가된 내용, 누락된 내용, 제외된 내용, 추가 확인이 필요한 내용으로 구분해 주세요.

각 판단의 근거 문서를 표시하고, 자료에 없는 내용은 추정하지 마세요.</code></pre>

여기서 핵심은 제안서를 요약하는 것이 아니라 문서 사이의 차이를 찾는 것입니다. 고객 요구와 일치하는 내용, 제안서가 새로 제시한 금액·일정, 누락되거나 제외된 내용을 서로 다른 범주로 분리합니다.

이후 제안서 검토 회의록이 도착했다고 가정합니다. 회의록을 프로젝트 소스에 추가한 뒤 새 채팅을 만들지 않고 제안서 검토 채팅으로 돌아갑니다.

<pre><code>프로젝트에 새로 추가된 제안서 검토 회의록을 확인하고, 기존 제안서와 비교해 변경 전과 변경 후를 표로 정리해 주세요.

변경되지 않은 제외 범위도 별도로 표시해 주세요.</code></pre>

변경 전후, 그대로 유지된 조건과 새로 확인해야 할 조건이 구분되면 변경 관리가 제대로 된 것입니다.

## 8. 실습 3: 계약서 검토와 킥오프 준비

계약서 초안을 소스에 추가합니다. 계약서 검토는 별도 결과물이므로 새 채팅을 만들고 `03. 계약서 검토와 프로젝트 준비`라고 이름을 붙입니다.

<pre><code>프로젝트의 문의 이메일, 상담 전사, 제안서, 회의록과 계약서 초안을 함께 비교해 주세요.

법률 검토가 아니라 업무 범위와 조건이 이전 합의와 일치하는지 확인해 주세요.

올바르게 반영된 내용, 회의 합의와 다른 내용, 누락된 내용, 새로 추가된 조건, 계약 전에 확인할 사항으로 정리해 주세요.

각 판단의 근거 문서와 해당 문구를 표시하고, 확실하지 않은 내용은 확인 필요로 남겨 주세요.</code></pre>

검토할 때는 다음 두 범주를 반드시 구분합니다.

* **불일치:** 이전 합의와 어긋나 수정 요청이 필요한 내용
* **새 조건:** 이전 자료에는 없어 오류라고 단정할 수 없고 확인이 필요한 내용

이 결과는 법률 자문이 아닙니다. 실제 계약은 담당자와 조직의 검토 절차를 거쳐야 합니다.

계약 조건이 정리되면 같은 채팅에서 킥오프 준비 목록을 만듭니다.

<pre><code>계약이 수정되어 체결된다고 가정하고, 프로젝트 킥오프 미팅 준비 체크리스트를 만들어 주세요.

고객에게 받아야 할 자료, 킥오프에서 확정할 사항, 프로젝트 위험요소를 포함해 주세요.
각 항목에는 담당자와 완료 기준을 적을 빈칸을 만들어 주세요.</code></pre>

## 9. 프로젝트를 안정적으로 운영하는 원칙

### 9.1 새 자료가 오면 관련 결과를 업데이트합니다

새 자료가 도착할 때마다 처음부터 다시 만들 필요는 없습니다. 소스를 추가하고 그 결과물을 만든 기존 채팅으로 돌아가 변경된 부분을 업데이트합니다.

### 9.2 출처와 최신성을 함께 확인합니다

프로젝트가 자료를 함께 참고한다고 해서 충돌이 자동으로 해결되는 것은 아닙니다. 문서의 날짜, 버전과 승인 여부를 확인하고 어떤 근거를 우선했는지 표시하게 합니다.

### 9.3 공유 전에 접근 범위를 점검합니다

프로젝트를 공유하면 초대된 사람이 프로젝트의 채팅, 파일, 지침과 연결된 맥락에 접근할 수 있습니다. 공유 전에 개인정보, 고객 정보, 계약 조건과 내부 지침을 점검하고 필요한 사람에게만 적절한 권한을 부여합니다.

프로젝트 공유 방식과 제공 범위는 플랜과 워크스페이스 설정에 따라 달라질 수 있으므로 실제 화면의 권한 설명을 확인합니다.

### 9.4 결과는 반드시 원문과 대조합니다

특히 금액, 일정, 법적 조건과 고객 요구사항은 AI가 만든 표만 믿지 않습니다. 결과의 핵심 항목을 원문에서 다시 확인하고 담당자가 승인한 최신 문서를 정본으로 삼습니다.

## 10. 자주 막히는 문제와 해결 방법

| 문제 | 원인 | 해결 방법 |
| --- | --- | --- |
| 새 채팅에서 배경이 반영되지 않음 | 프로젝트 밖에서 채팅을 시작함 | 프로젝트 안의 새 채팅인지 확인 |
| 오래된 조건이 우선됨 | 문서의 날짜·승인 상태가 불명확함 | 파일명과 본문에 버전·날짜를 표시하고 우선순위를 지침에 명시 |
| 결과가 너무 길고 뒤섞임 | 한 채팅에서 여러 결과물을 만듦 | 결과물의 목적별로 채팅을 분리 |
| 없는 내용을 사실처럼 작성함 | 자료의 경계와 처리 원칙이 없음 | “자료에 없으면 확인 필요”라고 지침과 프롬프트에 명시 |
| 민감한 자료가 노출될 수 있음 | 공유 범위와 업로드 정책을 확인하지 않음 | 샘플 자료로 실습하고 조직 정책·공유 권한을 먼저 점검 |

## 11. 실습 완료 기준

다음 항목을 모두 확인하면 실습이 완료된 것입니다.

* 프로젝트 이름, 지침과 소스가 준비되었습니다.
* 지침에는 공통 역할과 원칙만 있고 변동 사실은 소스에 있습니다.
* 요구사항, 제안서 검토와 계약서 검토가 목적별 채팅으로 나뉘었습니다.
* 서로 다른 문서의 정보가 근거와 함께 결합되었습니다.
* 회의록 추가 후 변경 전후가 갱신되었습니다.
* 계약 불일치와 새 조건이 구분되었습니다.
* 핵심 금액, 일정과 범위를 원문에서 다시 확인했습니다.
* 공유와 보안 범위를 점검했습니다.

## 12. 핵심 정리

* 프로젝트는 관련 채팅, 파일, 지침과 연결된 소스를 하나의 업무 맥락으로 관리합니다.
* 같은 주제로 다시 돌아오고 자료와 조건이 계속 바뀌는 일이 프로젝트에 적합합니다.
* 지침은 역할과 원칙, 소스는 사실과 근거를 담당합니다.
* 채팅은 시간 순서가 아니라 결과물의 목적별로 나눕니다.
* 새 자료가 오면 관련 채팅으로 돌아가 바뀐 부분을 업데이트합니다.
* 문서 비교에서는 일치, 불일치, 누락과 새 조건을 구분합니다.
* 공유 전에는 접근 범위와 민감정보를 점검하고, 결과의 핵심 사실은 원문과 대조합니다.

현재 프로젝트의 기본 구조와 사용 방식은 [OpenAI 프로젝트 공식 가이드](https://learn.chatgpt.com/docs/projects)에서 확인할 수 있습니다.
